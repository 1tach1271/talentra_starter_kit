# Integration Boundary Table — Section 6

**Project:** Talentra  
**Version:** Schema v1  
**Date:** 2026-10-20  
**Reference:** Docket Section 6 — External System Boundaries

This table defines the integration boundary for every external system that Talentra touches. For each system it states: what Talentra stores, what it does **not** store, the source of truth, how failures are handled, how idempotency is guaranteed, and how every interaction is audited.

---

## Integration Boundary Matrix

| # | External System | Source of Truth | What Talentra Stores | What Talentra Does NOT Store | Failure Handling | Idempotency Guarantee | Audit Trail |
|---|---|---|---|---|---|---|---|
| 1 | **Payment Gateway** (Stripe / Razorpay / equivalent) | Payment gateway | `payment_order` row: `amount`, `currency_id`, `payment_status_id`, `gateway_reference`, `idempotency_key`, `paid_at`. On success: `wallet_ledger` credit entry + `invoice` row. | Raw card numbers, CVV, bank account details, PCI-scoped tokenisation keys. | Order is created locally in `payment_order` with `status = 'created'`. If gateway call fails or times out, the row remains `pending`; a background polling job retries using the stored `idempotency_key`. No money is credited until the gateway confirms `paid`. | `uq_payment_order_idempotency_key` UNIQUE constraint on `payment_order.idempotency_key`. The same key is re-submitted to the gateway; gateway idempotency + local UNIQUE constraint together guarantee exactly-once credit. | `payment_order` row lifecycle (created → paid/failed); `wallet_ledger` append-only entry on success; `invoice` row issued on payment confirmation. All writes carry `created_by` / `updated_by` audit columns. |
| 2 | **Identity Verification Service** (KYC / AML provider) | Verification service | `organisation.verification_status_code` + `organisation.verification_token` (encrypted at rest). Verification event recorded in `audit_log`. | Raw national ID numbers in cleartext. Government-issued document images. Any PII that the verification service processes internally. | Organisation is held in `pending_verification` status, blocking full-posting capability. A webhook / callback from the verification service updates the status; if the webhook fails, the status remains `pending_verification` and the service re-delivers. | The `verification_token` issued by the provider serves as the idempotency key. Re-delivering the same webhook with the same token is a no-op (status is already set). | `audit_log` entry on every status transition (e.g., `pending_verification → verified`, `verified → suspended`). `updated_by` and `updated_at` on `organisation`. RLS in `09_security_rls.sql` prevents unverified organisations from accessing recruiter-tier features. |
| 3 | **Company Registration & Tax Verification** (Government registry / company house) | Government registry | `organisation_identifier` table rows: `(organisation_id, identifier_type, value, country_id)`. Verification status flag on `organisation`. | Full registry API responses. Historical company filing documents. | On registration mismatch or registry API failure, `organisation.verification_status_code` is set to `unverified`; the organisation may post jobs with a visible "Unverified" badge but cannot access premium features. A retry job re-queries the registry. | `(organisation_id, identifier_type)` UNIQUE constraint on `organisation_identifier`. Submitting the same identifier type for the same organisation is idempotent — the row already exists and is updated in-place rather than duplicated. | `audit_log` entry on every status change. `created_at` / `updated_at` on `organisation_identifier`. Manual override by `app_admin` role is auditable via `updated_by`. |
| 4 | **Gig Fulfilment System** (external workforce management platform) | Fulfilment system | `gig_assignment.fulfilment_reference` (external reference set on handoff). `gig_earning_reference` row: `(gig_assignment_id, external_reference, amount, currency_id, reconciled_at)`. | Internal fulfilment workflow state (shift scheduling, check-in/check-out events). Worker payroll details held by the fulfilment system. | `gig_assignment` remains in `accepted` state until the fulfilment system confirms completion and pushes a reconciliation event. The reconciliation job retries on next sync cycle; `reconciled_at` is set exactly once on success. | `uq_gig_earning_reference_external` UNIQUE constraint on `gig_earning_reference.external_reference`. Re-syncing the same earning event with the same external reference is a no-op. | `gig_earning_reference` row is append-only in practice (`reconciled_at` stamped once; no DELETE path). `sp_add_audit('gig_earning_reference')` tracks `created_at` / `created_by`. `gig_assignment` carries full audit columns. |
| 5 | **Legacy Job & Candidate Systems** (pre-Talentra data stores) | New Talentra DB (post-cutover) | Full migrated records in the canonical Talentra schema (`candidate_profile`, `job_requirement`, `application`, etc.). | Original legacy system tables; quarantine rows (not in schema v1 — see deviation). | Migration job retries on transient failures. Rows that fail validation rules (e.g., duplicate email) are rejected. Before cutover: latest `updated_at` wins on conflict. After cutover: Talentra record wins unconditionally. | `email` and `phone_e164` UNIQUE constraints on `app_user` and `candidate_profile` prevent duplicate import of the same person. Combined with `created_by = <migration_system_user_id>` they provide an idempotent migration path. | `created_by` on migrated rows is set to a dedicated system user (e.g., `app_user_id = 1`, migration bot). `created_at` reflects the migration timestamp; `audit_log` records the import event. **Deviation:** a `migration_quarantine` table for rejected rows is not in schema v1; quarantine logging deferred to v2. |
| 6 | **Messaging & Notification Providers** (SendGrid / Twilio / equivalent) | Talentra (originator) | `notification` table row: `event_code`, `recipient_app_user_id`, `delivery_status`, `sent_at`, `last_attempt_at`, `attempt_count`, `audit_snippet` (truncated message preview). | Full message body beyond the audit snippet. Provider-internal delivery logs. | Notification row is created with `status = 'pending'`. Background worker retries delivery up to 3 times with exponential backoff. After 3 failures, status transitions to `failed` and an alert is raised. Non-delivery does not block the originating business transaction. | `notification.idempotency_key` (if populated by the caller) enforces deduplication at the DB layer. Alternatively, the composite `(event_code, entity_id, created_at window)` is used to detect near-duplicate sends before dispatch. | `notification` row lifecycle tracked via `delivery_status` updates (`pending → sent → delivered / failed`). `created_at`, `sent_at`, `last_attempt_at` provide a full timeline. RLS in `09_security_rls.sql` restricts notification reads to `app_admin`. |
| 7 | **Social Sharing** (LinkedIn, WhatsApp, X / Twitter) | Talentra (share event originator) | Share event: `(entity_type, entity_id, platform, shared_at, app_user_id)`. **Not in schema v1 — Tier 3 feature.** | OAuth tokens for social platforms (stored separately in a credentials vault if implemented). Engagement metrics from social platforms. | Non-critical integration. On failure, the share action fails silently from the user's perspective; no retry. The share event row is simply not written if the external platform call fails. | Composite `(entity_id, platform, app_user_id)` UNIQUE constraint on the share event table prevents recording the same share twice. | Share event row with `shared_at` timestamp. Not subject to audit trigger chain in v1 (append-only insert is sufficient). |
| 8 | **Mapping & Geolocation Service** (Google Maps API / OpenStreetMap / GeoNames) | Geolocation provider | `city.latitude`, `city.longitude`, `city.name` seeded from GeoNames during master data load. `city_id` FK used throughout (`job_requirement.city_id`, `gig_request.city_id`, `candidate_profile.city_id`). | Live routing data. Real-time distance calculations. Dynamic geocoding results (not persisted beyond initial seed). | On geolocation API failure: fall back to city-level matching using the pre-seeded `city` table. Distance-based search degrades gracefully to city-name or region-level filtering. No data loss — the stored city master data is self-contained. | `city_id` is the stable, pre-seeded reference key. Geolocation calls are read-only lookups; no write path requires idempotency handling. Re-seeding master data uses `ON CONFLICT DO NOTHING` or `DO UPDATE` on the `city.name + country_id` natural key. | Not required for read-only lookups. Master data re-seeding is logged via the standard `created_at` / `updated_at` audit trail on the `city` table. |
| 9 | **Company Review & Salary Data** (Glassdoor-equivalent provider) | Third-party review provider | `employer_review_snapshot` table: `(organisation_id, source, snapshot_date, avg_rating, review_count, data_json)`. **Not in schema v1 — Tier 3 feature.** | Individual reviewer identities. Raw verbatim review text (only aggregated stats stored). | On provider API failure: display the last cached snapshot. Snapshot age is surfaced to the end user. No staleness hard limit in v1; a freshness check (e.g., `snapshot_date < now() - interval '7 days'`) triggers a background refresh. | `(organisation_id, source, snapshot_date)` UNIQUE constraint on `employer_review_snapshot` prevents duplicate snapshots for the same org + source + date. | `snapshot_date` and `created_at` on the snapshot row serve as the audit trail. Background refresh timestamp recorded in `updated_at`. No `app_user` actor — `created_by` / `updated_by` set to the system service account. |

## Notes

1. **Tier 3 systems (rows 7, 9):** Social sharing and company review/salary data are explicitly deferred to a future schema version. Their integration boundary definitions above are forward-looking designs to be implemented when Tier 3 is prioritised.

2. **Security boundary (RLS):** `09_security_rls.sql` defines three roles (`app_candidate`, `app_recruiter`, `app_admin`). RLS policies on `wallet_ledger`, `candidate_profile`, `job`, and `application` enforce the boundaries between these roles at the database layer, independently of application-level access control. External system integrations that write to these tables must do so via the `app_admin` role or a dedicated service role.

3. **Idempotency principle:** Every external write path that Talentra controls uses a `UNIQUE` constraint on an `idempotency_key` or a natural business key. This ensures that network retries from any external system never produce duplicate records.
